# Spec: Q10

Version 1.2. Fecha: 2026-11-17. Responsable: equipo tecnico CIUNAC. Estado: Implementado (AS-IS). Historias HU-Q10-001/002 y evidencia en [matriz SDD](traceability.json). Ver [guia frontend](../frontend/integration.md) y [contrato de errores y logs](../frontend/q10-registration-errors.md); no se acredita aqui una pantalla.

## Objetivo funcional

Integrar CIUNAC Backend con Q10 para crear estudiantes y sincronizar horarios/cursos.

El alta incluye [estudiante nuevo (HU-EST-002)](estudiante-nuevo.md): `tipoEstudiante` (`PRE`/`POS`/`PG`) e `imgDoc` son opcionales y pertenecen exclusivamente a la tabla local `estudiantes`. PRE/POS con escuela requieren compatibilidad de tipo; PG admite facultad y escuela opcionales. Los cuatro campos locales se excluyen del payload Q10. Ejecutar previamente el SQL de `escuelas.tipo` documentado en la feature.

## Actores

- Administrador academico.
- Sistema Q10.
- Frontend administrativo.

## Precondiciones

- `API_KEY` valida para consumir endpoints del backend.
- `API_KEY_Q10` configurada para consumir Q10.
- Datos minimos del estudiante disponibles.

## Flujo principal

1. El frontend solicita crear estudiante en `POST /q10/estudiantes`.
2. El backend valida el catalogo efectivo (IDs nuevos no nulos o persistidos). Para PRE/POS, una escuela debe estar clasificada y tener el mismo tipo; PG o ausencia de tipo no exigen coincidencia. Un error devuelve `400` antes de cualquier llamada a Q10.
3. `Q10Service` separa esos campos locales e invoca Q10 con credenciales configuradas, sin enviarlos a la API externa.
4. Q10 devuelve `Codigo_estudiante`; el backend lo valida como obligatorio.
5. El backend reconcilia al estudiante local por `numeroDocumento`, guarda `id_q10` y los campos locales proporcionados en `facultad_id`, `escuela_id`, `tipo_estudiante` e `img_doc`.
6. El backend registra al estudiante en el programa Q10.
7. El administrador consulta horarios con `GET /q10/horarios-cursos`.
8. El administrador guarda horarios/cursos con `POST /q10/horarios-cursos`.

## Flujos alternos y errores

| Caso                                                | Resultado                                                                                                                   |
| --------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Facultad local inexistente                          | `400` con `La facultad indicada no existe`, antes de llamar a Q10.                                                          |
| Escuela local inexistente                           | `400` con `La escuela indicada no existe`, antes de llamar a Q10.                                                           |
| Escuela de otra facultad cuando se envian ambos IDs | `400` con `La escuela indicada no pertenece a la facultad indicada`, antes de llamar a Q10.                                 |
| Q10 rechaza creacion                                | `400 Bad Request` con informacion controlada.                                                                               |
| No se pudo comunicar con Q10 al crear               | `502 Q10_UNAVAILABLE`, retryAllowed=false; revisar el estado remoto antes de repetir una escritura incierta. |
| Consulta de periodo fallida o sin consecutivo valido | `502 Q10_PERIOD_LOOKUP_FAILED`, retryAllowed=false; no se envia el POST de alta. |
| Q10 crea, pero no devuelve `Codigo_estudiante`      | `502` con `Q10_CREATED_INVALID_RESPONSE` y sin reintento automatico.                                                        |
| Q10 crea, pero falla PostgreSQL                     | `502` con `Q10_CREATED_LOCAL_SYNC_FAILED`, `idQ10` y sin reintento automatico.                                              |
| Documento local asociado a otro `idQ10`             | `409 Conflict` con `Q10_ID_CONFLICT`.                                                                                       |
| `idQ10` asociado a otro estudiante                  | `409 Conflict` con `Q10_ID_ALREADY_LINKED`.                                                                                 |
| Estudiante local guardado, pero falla la matricula  | `502` con `Q10_CREATED_PROGRAM_PENDING`, `estudianteId`, `idQ10` y sin reintento automatico.                                |
| Falla al listar horarios                            | `400 Bad Request`.                                                                                                          |
| Falla al guardar horarios                           | `400 Bad Request`.                                                                                                          |
| API key backend invalida                            | `401 Unauthorized`.                                                                                                         |

## Reglas de negocio

- La integracion Q10 queda encapsulada en `Q10Service`.
- `estudiantes.id` conserva el UUID interno; `estudiantes.id_q10` almacena exclusivamente `Codigo_estudiante`.
- `id_q10` no forma parte de los DTOs genericos de crear/actualizar estudiantes.
- La sincronizacion busca por `numeroDocumento` y nunca crea un duplicado cuando el estudiante ya existe.
- El mismo documento y el mismo `idQ10` constituyen una operacion idempotente.
- `facultadId` y `escuelaId` son IDs locales opcionales, enteros positivos; no se envian a Q10 ni forman parte de su respuesta.
- `tipoEstudiante` e `imgDoc` son opcionales; solo se guardan en PostgreSQL. Tipo admite PRE/POS/PG; documento requiere URL HTTP/HTTPS absoluta no vacia cuando se proporciona. Omitirlos o enviar null conserva lo existente.
- Si se omite tipo para un estudiante existente, la validacion usa el tipo almacenado. PRE/POS rechazan escuelas incompatibles o sin clasificar; PG permite relaciones academicas sin validar coincidencia de tipo.
- Se puede enviar cada ID individualmente. No se infiere automaticamente el otro; la pertenencia se comprueba cuando se proporcionan ambos.
- En un estudiante existente solo se actualizan los IDs academicos proporcionados. Omitirlos o enviar `null` conserva sus valores actuales; este endpoint no los borra.
- El frontend no debe reintentar automaticamente los fallos parciales con `retryAllowed: false`.
- Errores de Q10 deben transformarse a excepciones controladas.
- El alta registra errores controlados e inesperados con operationId, etapa, HTTP, codigo y reglas permitidas, sin datos personales ni mensajes crudos externos. El header X-Operation-Id correlaciona respuesta y logs. Inscripcion invalida detiene la matricula y devuelve Q10_CREATED_PROGRAM_PENDING.
- Direccion, Lugar_nacimiento, Lugar_residencia, Consecutivo_sedejornada y Consecutivo_periodo son opcionales tambien en Swagger. El servicio conserva su comportamiento: establece los valores de Q10 al armar el payload remoto. No se modifican esas reglas por cambiar metadata.
- tipoEstudiante nullable incluye null dentro del enum OpenAPI; sus reglas de negocio no cambian.
- No deben registrarse secrets de Q10 en logs.

### Registro con facultad y escuela locales

Una sola llamada a `POST /q10/estudiantes`, con headers `Content-Type: application/json` y `x-api-key: <API_KEY>`, permite registrar al alumno en ambos sistemas:

```json
{
  "Primer_nombre": "Ana",
  "Segundo_nombre": "Maria",
  "Primer_apellido": "Perez",
  "Segundo_apellido": "Lopez",
  "Email": "ana@example.com",
  "Codigo_tipo_identificacion": "PE01",
  "Numero_identificacion": "12345678",
  "Genero": "F",
  "Fecha_nacimiento": "2000-01-01",
  "Telefono": "014444444",
  "Celular": "999999999",
  "Direccion": "Lima",
  "Codigo_programa": "INGLES",
  "facultadId": 3,
  "escuelaId": 8,
  "tipoEstudiante": "PRE",
  "imgDoc": "https://drive.google.com/file/d/ID_DEVUELTO_POR_UPLOAD/view"
}
```

Los IDs son ejemplos y deben reemplazarse por valores existentes del catalogo local. Usar los nombres camelCase `facultadId` y `escuelaId`, aunque las columnas SQL usan snake_case. Los clientes actuales pueden omitir ambos campos.

| Campo            | Tipo                     | Comportamiento                                                                            |
| ---------------- | ------------------------ | ----------------------------------------------------------------------------------------- |
| `facultadId`     | Entero positivo opcional | Se guarda en `estudiantes.facultad_id`; omitido o `null` conserva el valor existente.     |
| `escuelaId`      | Entero positivo opcional | Se guarda en `estudiantes.escuela_id`; omitido o `null` conserva el valor existente.      |
| `tipoEstudiante` | PRE/POS/PG opcional      | Se guarda en `estudiantes.tipo_estudiante`; omitido o `null` conserva el valor existente. |
| `imgDoc`         | URL HTTP/HTTPS opcional  | Se guarda en `estudiantes.img_doc`; omitido o `null` conserva el valor existente.         |

La respuesta exitosa sigue siendo `201` con `status`, `estudiante: { id, idQ10, numeroDocumento }` y `programaRegistrado`. Los IDs academicos no se agregan a esa respuesta. Para un error de catalogo, por ejemplo:

```json
{
  "message": "La escuela indicada no pertenece a la facultad indicada",
  "error": "Bad Request",
  "statusCode": 400
}
```

## Datos involucrados

- PostgreSQL: `estudiantes.id_q10 varchar(100)`, nullable, con indice unico parcial.
- PostgreSQL: columnas existentes `estudiantes.facultad_id`, `estudiantes.escuela_id`, `estudiantes.tipo_estudiante` e `estudiantes.img_doc`. La clasificacion requiere agregar `escuelas.tipo` con [el SQL controlado](../sql/add-tipo-to-escuelas.sql), sin modificar estudiantes historicos.
- DTOs: `q10-estudiante.dto.ts`, `q10-estudiante-response.dto.ts`, `q10-horarios.dto.ts`.
- Entidades relacionadas segun guardado de horarios/cursos.

## Criterios de aceptacion

- Dado un estudiante valido, cuando se envia a Q10, entonces se devuelve resultado de creacion o error controlado.
- Dado un request con IDs academicos validos, estos se guardan localmente y no aparecen en ninguna peticion enviada a Q10.
- Dado un ID academico inexistente o una combinacion incompatible, el backend devuelve `400` antes de contactar a Q10.
- Dado un estudiante existente, los IDs omitidos o `null` mantienen sus valores anteriores.
- Dado que Q10 devuelve `Codigo_estudiante`, cuando la sincronizacion termina, entonces la respuesta contiene el UUID local y `idQ10`.
- Dado un estudiante local con el mismo documento y sin `idQ10`, cuando Q10 lo crea, entonces se actualiza el registro existente.
- Dado un conflicto entre documento e `idQ10`, cuando se sincroniza, entonces se responde `409` sin sobrescribir la vinculacion existente.
- Dado un fallo posterior a la creacion remota, cuando se responde al frontend, entonces `retryAllowed` es `false`.
- Dado un rechazo de alta por Q10, responde 400; si falla la comunicacion al crear, responde 502 Q10_UNAVAILABLE. No se exponen secrets.
- Dado horarios validos, cuando se guardan, entonces quedan disponibles para operacion interna.
